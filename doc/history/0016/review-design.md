## 设计优点

### 1. 职责清晰

**优点**: 将日志查询功能分散到任务面板，符合单一职责原则

**分析**: 
- 监控页面负责全局日志查询
- 任务面板负责任务相关日志查询
- 职责边界明确，易于维护

### 2. 向后兼容

**优点**: 保持现有全局日志查询功能不变

**分析**:
- metaId 参数为可选参数
- 不传 metaId 时，查询所有日志
- 不影响现有用户习惯

### 3. 用户体验提升

**优点**: 减少跨页面跳转

**分析**:
- 用户可在任务详情页面直接查看日志
- 上下文更明确，减少混淆
- 操作流程更简洁

## 设计问题

### 问题 1: 代码重复

**描述**: 任务面板和全局监控页面存在相似的日志查询 UI 代码

**影响**: 维护成本增加

**建议**:
- 将日志查询 UI 组件抽取为公共模块
- 使用 JavaScript 模块化管理

### 问题 2: 日志存储结构

**描述**: 日志表未明确记录 metaId 字段

**影响**: 可能无法准确关联日志到任务

**建议**:
- 检查 `LogVo` 对象是否包含 metaId 字段
- 验证 `LogService` 是否正确记录 metaId

### 问题 3: 清空日志范围

**描述**: 清空日志功能需要区分全局清空和任务清空

**影响**: 可能误清空其他任务日志

**建议**:
- 新增 `/monitor/clearLog` 参数支持按 metaId 清空
- 或保留两个接口：`/monitor/clearLog`（全局）和`/monitor/clearTaskLog`（任务）
