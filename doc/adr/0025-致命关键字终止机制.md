# 致命关键字终止机制

当错误消息匹配预定义的致命关键字时，立即终止同步任务，跳过错误队列写入和计数。

## 背景

现有错误处理机制：
- **错误队列**：可恢复的错误写入队列，供运维重试
- **熔断器**：错误累计达到阈值后自动停止任务

某些错误本质上是不可恢复的（如数据损坏、约束违反），继续执行只会产生更多垃圾数据。需要一种"即时判定"机制，在第一次命中时就终止任务。

## 决策

### 1. 术语

使用 **fatal-keywords**（致命关键字），而非"黑名单"。语义更精确：描述的是"什么错误意味着死亡"，而非"谁被禁止"。

### 2. 执行位置

在 `handleFailData` / `handleDdlFailData` 中：

```
1. logger.error(...)
2. logService.log(...)
3. notifyError(...)
4. if (isErrQueueRetry) throw e;
5. ★ 致命关键字检查 → 命中则 closeTask, return
6. persistError(...)
7. counterService.incrementFail(...)
8. checkCircuitBreaker(...)
```

- 日志和通知照常执行
- 跳过错误队列写入和失败计数
- 在熔断检查之前执行

### 3. 匹配行为

- 匹配对象：`e.getMessage()`（不递归异常链）
- 匹配模式：独立配置 `match-mode`，代码复用 `KeywordMatcher` 工具类
- 空值处理：`e.getMessage()` 为空不触发，配置中的空串忽略
- 适用范围：DDL 错误和数据同步错误

### 4. 配置

```properties
# 致命关键字匹配模式（EXACT/CONTAINS/CASE_INSENSITIVE/CONTAINS_IGNORE_CASE）
dbsyncer.error.fatal-match-mode=CONTAINS_IGNORE_CASE
# 致命关键字列表
dbsyncer.error.fatal-keywords[0]=ORA-00001
dbsyncer.error.fatal-keywords[1]=Duplicate entry
```

先只做全局配置，任务级覆盖留作后续扩展。

### 5. 通知类型

新增 `NotifyType.DATA_ERROR_FATAL`，显示名称"致命错误"。

### 6. 并发安全

依赖 `CircuitBreakerEventListener.onCircuitBreak` 中的 `!meta.isRunning()` 守卫，防止任务被重复关闭。

## 后果

- 致命错误不会出现在 UI 的"错误队列"页面（因为没写错误队列）
- 运维通过通知消息和系统日志感知任务终止原因
- 与熔断机制并列，不互相干扰
