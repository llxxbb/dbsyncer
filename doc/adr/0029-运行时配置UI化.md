## 术语

| 术语 | 含义 |
|------|------|
| **Tab 子对象（Props）** | 按 UI Tab 组织的嵌套配置对象，与 `SystemConfig` 现有平铺字段并存 |
| **整块替换（tab-scoped replace）** | 保存某 Tab 时用提交的 payload 完整替换对应子对象，不做字段级 merge |
| **未配置（null 语义）** | 子对象为 `null` 表示该 Tab 从未在 UI 保存过，运行时回退到 `application.properties` |
| **NON_DEFAULT** | `JsonUtil` 实际生效的序列化策略（F6），等于 Java 字段初始值的属性不落库 |
| **sidecar** | 由 UI 保存动作派生出的明文启动缓存文件，供 refresh 前读取（见 §2） |
| **A/B/C 类** | A=只能重启且不宜 UI 编辑；B=需重启但可 UI 编辑；C=运行期热读、立即生效 |

## 背景

系统配置页（`/system`）目前只暴露 `SystemConfig` 的 **10 个字段**（F1），页面是 85 行的单表单（F18）。
除此之外，约 **40 项**运行时参数只存在于 `application.properties`，改一次要 SSH 登录服务器 + 重启 JVM：

| 组 | 项数 | 归属 Bean |
|----|------|-----------|
| 线程池 | 10 | `GeneralBufferConfig`/`StorageConfig`/`DispatchTaskConfig` 各 3 + `SchedulerConfig` 1（F9） |
| 缓冲区 | 8 | `BufferActuatorConfig` 4 字段 × general/storage 两处（F9、F11） |
| 重试策略 | 11 | `RetryPolicy`（F15） |
| 错误处理 | 3 | `ErrorQueueConfig`（F17c） |
| 通知通道 | 7 | `NotifyConfig.channels` + `MailConfig` 3 + `DingTalkConfig` 3（F16） |
| 安全 | 1 | `WebAppConfig.resetPwd`（F17） |

**问题**：
1. 运维门槛高：改参数必须登录服务器。
2. 配置分散：散落在 `dbsyncer.parser.general.*`、`dbsyncer.storage.*`、`dbsyncer.common.dispatch.*`、
   `dbsyncer.web.scheduler.*`、`dbsyncer.retry.*`、`dbsyncer.error.*`、`dbsyncer.plugin.notify.*` 七个前缀下。
3. 无审计：`SystemConfig` 走 `dbsyncer_config` 表有 `UPDATE_TIME`（F4），properties 侧改动完全无记录。

**根因（F3）**：工程里存在**两套互不相通的配置源**——DB 侧 `SystemConfig`（经 `OperationTemplate`
内存缓存，编辑即生效，F5）与 Spring 侧 `@ConfigurationProperties` Bean（仅启动时绑定）。
本 ADR 的本质是**把第二套接进第一套**，而不是给第一套加字段。

## 决策

将 B+C 类配置 UI 化，以**按 Tab 组织的嵌套子对象**扩展 `SystemConfig`，并通过
**refresh 前的 `EnvironmentPostProcessor`（读 sidecar）** 解决 B 类的启动期生效问题。

### 1. 数据模型：SystemConfig 结构重构

SystemConfig 根节点不留具体配置项，所有配置都组织成子配置类。

```java
public class SystemConfig extends ConfigModel {
    private int schemaVersion;  // 配置版本号，默认 0

    // === A 类（只读，UI 脱敏显示） ===
    private ServerProps server;                    // server.port, server.ssl.*, server.http.port
    private StorageConnectionProps storageConn;    // dbsyncer.storage.type, mysql.*
    private LoggingProps logging;                  // logging.level.root
    private HelpdocProps helpdoc;                  // helpdoc.path
    private WorkerProps worker;                    // dbsyncer.web.worker.id, data-center-id
    private LicenseProps license;                  // dbsyncer.web.license.server.address

    // === B 类（需重启） ===
    private ExecutorProps executors;               // Tab 2，null=未覆盖
    private BufferProps   buffers;                 // Tab 3，null=未覆盖

    // === C 类（立即生效） ===
    private RetryProps retry;                      // Tab 4，null=未覆盖
    private NotifyProps notify;                    // Tab 5，null=未覆盖
    private ErrorProps error;                      // Tab 6，null=未覆盖

    // === 基础设置（原扁平字段组织成子对象） ===
    private BasicProps basic;                      // expireDataDays, expireLogDays, ...
}
```

**好处**：
1. **统一管理**：所有配置都在 SystemConfig 里，不管是 A/B/C 类
2. **迁移一致**：首次运行时，所有配置都从 bean 迁移到 DB
3. **结构清晰**：SystemConfig 变成纯容器，所有具体配置都在子对象里
4. **UI 一致**：A 类配置在 UI 上只读显示（脱敏），数据存在 DB

Props 类放 `dbsyncer-common`（`SystemConfig` 在 parser、目标 Bean 也在 common，两侧可见，F19）。

> **S1 修订：Props 字段必须使用包装类型**（`Integer`/`Boolean`/`Double`/`Long`），不用基本类型。
> 原因：`JsonUtil` 使用 `NON_DEFAULT` 策略（F6），基本类型 `int` 的 Java 默认值 `0` 与用户显式设置的 `0`
> 不可区分——`threshold=0`（不熔断）、`maxDurationMs=0`（不限时长）等合法业务值会被 NON_DEFAULT 省略，
> 反序列化后回退到 properties 值而非保持 `0`。使用包装类型后 Java 默认 = `null`，`null` 被省略 →
> 反序列化 `null` → 回退 properties ✓；显式设 `0` → `Integer(0)` ≠ null → 序列化 ✓。
> 同理 `boolean` → `Boolean`、`double` → `Double`。

**为什么用子对象而非把 40 项展平进 `SystemConfig`**：

| 收益 | 依据 |
|------|------|
| Tab 独立保存 | 一个 Tab = 一个子对象 = 一次整块替换，无需字段级 merge |
| 消除字段级 sentinel 歧义 | F6：`NON_DEFAULT` 下"值等于默认"与"未设置"不可区分；只能用**对象级 null** 表达"未覆盖" |
| 避开 `BeanUtil.mapToBean` | F7：现有表单通道只认扁平精确字段名 + 6 种标量，未知 key 直接 NPE——展平方案必须改造它，子对象方案可以完全不碰 |
| 不动表结构 | F4：整对象序列化进单个 `JSON mediumtext` 列，Jackson 原生支持嵌套 |
| 存量兼容 | 旧 JSON 无这些字段 → 反序列化为 `null` → 行为与今天完全一致 |
| 映射表收敛 | Props 字段名与目标 Bean **逐字对齐**，回写退化为按 Tab 的 `copyProperties` |
| 结构清晰 | SystemConfig 变成纯容器，所有具体配置都在子对象里，便于管理和迁移 |

> `NON_DEFAULT` 序列化策略下，字段值 `0` 与"未设置"不可区分：
> `threshold=0` 的业务含义是"不启用熔断"（F17c `ErrorQueueConfig:20` 默认值本就是 0）、
> `maxDurationMs=0` 是"不限制时长"（F15 `RetryPolicy:29`）——都是合法业务值，无法与"未设置"区分。
> 因此只能用**对象级 null** 表达"未覆盖"。

### 1.1 配置迁移与版本管理

**SystemConfig 增加 `schemaVersion` 字段**：
- 类型：`int`，默认 `0`
- 用途：
  - **迁移判定**：`schemaVersion=0` 表示未迁移，迁移完成后置为 1，后续结构变更再递增
  - **防回退**：避免旧版 JSON 反序列化后静默丢失新字段

**首次运行迁移逻辑**：
```
PreloadTemplate.onApplicationEvent
  ↓
检测 schemaVersion == 0
  ↓ 是
从 @ConfigurationProperties bean 读运行时值
  ↓
写入 SystemConfig 的 sub-object JSON
  ↓
置 schemaVersion = 1
  ↓
打印"配置迁移完成"日志
```

**迁移源**：bean 运行时值（Spring relaxed binding 已归一化，不用自己解析 key 命名）。

**迁移范围**：
- ~~A 类：从 Spring Environment 读取~~ → **M5 修订：A 类不迁移、不落库**（`@JsonIgnore`，读时从 Environment 现取）
- B+C 类：从 @ConfigurationProperties bean 读取（`bean.getXxx()`）
- BasicProps：从原 SystemConfig 的 10 个平铺字段迁移

**迁移完成后**：
- `schemaVersion = 1`
- 所有配置都在 DB 里，application.properties 只作为回退
- 后续版本如需改结构，递增 `schemaVersion` 并写对应迁移逻辑

```
╠══════════════════════════════════╦═════════╦═════════╦═════╣

╠══════════════════════════════════╬═════════╬═════════╬═════╣

║ parser.general.buffer-queue-...  ║ 30000   ║ -       ║30000║

╚══════════════════════════════════╩═════════╩═════════╩═════╝
```

**打印时机**：`PreloadTemplate.onApplicationEvent` 完成后，`openStartupGates()` 之前。

**打印内容**：
- 配置项：properties key
- props：application.properties 的值（无则 `-`）
- DB：SystemConfig 的值（无则 `-`）
- 最终：实际生效值

### 1.3 配置变更安全机制

**前置校验（替代事后回滚）**

| 时机 | 校验内容 | 失败处理 |
|---|---|---|
| **保存前**（POST /system/editTab） | B 类字段范围检查（线程数>0、队列容量合理范围等） | 返回 400 + 字段错误，拒绝保存 |
| **启动前**（RuntimeConfigApplier.applyAll） | 全量校验 | 跳过该字段 + warn 日志 + 用默认值 + UI 横幅 |

**校验器示例**（约 60 行）：
```java
public class RuntimeConfigValidator {
    /** L4 修订：所有子对象先判 null，避免 NPE */
    public static List<String> validate(ExecutorProps exec) {
        List<String> errors = new ArrayList<>();
        if (exec == null) return errors;  // 未配置 = 不校验
        if (exec.getGeneral() != null) {
            PoolProps g = exec.getGeneral();
            if (g.getThreadCoreSize() != null && g.getThreadCoreSize() < 1) {
                errors.add("执行器核心线程数必须 > 0");
            }
            if (g.getThreadCoreSize() != null && g.getMaxThreadSize() != null
                && g.getThreadCoreSize() > g.getMaxThreadSize()) {
                errors.add("核心线程数不能大于最大线程数");
            }
        }
        if (exec.getDispatch() != null) { /* 同上 */ }
        if (exec.getStorage() != null) { /* 同上 */ }
        return errors;
    }
}
```

**UI 变更**：
- 保存前校验失败 → 表单字段标红 + 错误提示
- 启动后校验失败 → 页面顶部横幅"部分配置无效，请检查系统日志"

### 2. 生效机制

| 类别 | 机制 | 需要重建代码 |
|------|------|--------------|
| **A 类** | 仅 `application.properties`，UI 只读展示（密钥脱敏） | — |
| **B 类** | 保存时把该 Tab 的键写入 **sidecar 明文文件**；`EnvironmentPostProcessor` 在 refresh **之前**把 sidecar 作为最高优先级 `PropertySource` 注入 → `@Bean` 线程池方法首次执行即拿到 DB 值。**保存后自重启**（发消息通知 + 延迟 3 秒 + 优雅停机） | **否** |
| **C 类** | 启动期同 B（目标也全是 `@ConfigurationProperties` Bean，绑定瞬间即终态）；运行期由 `POST /system/editTab` **原地 setter** 回写目标 Bean | **否** |

### 2.1 B 类自重启流程

**保存后 → 自重启**

| 配置组 | 重启方式 | 实现 |
|---|---|---|
| `parser.general.buffer-*` | 驱动重启 | stop 该驱动（drain buffer）→ start |
| `storage.buffer-*` | 应用重启 | 优雅停机 → 重启 JVM |
| 执行器线程池 | 应用重启 | 同上 |

**自重启流程**：
```
保存成功 → 返回 hasRestartRequired=true
  ↓
UI 弹窗"配置已保存，需要重启生效。是否立即重启？"
  ↓ 用户确认
后端调用 System.exit(0) 或 Spring Boot graceful shutdown
  ↓
外部监控脚本（如 systemd）自动拉起
  ↓
启动时 → 前置校验 → 通过 → 应用新值
```

**重启前发消息通知**：
```java
// 保存成功后，需要重启
if (hasRestartRequired) {
    // 1. 发送通知
    String message = String.format(
        "系统参数已更新，应用即将重启。\n" +
        "操作人：%s\n" +
        "变更配置：%s\n" +
        "重启时间：%s",
        currentUser,
        changedConfigKeys,
        LocalDateTime.now()
    );
    notifyService.sendSystemNotification(message);  // 邮件/钉钉
    
    // 2. 延迟 3 秒后重启（给通知发送时间）
    Thread.sleep(3000);
    
    // 3. 优雅停机
    System.exit(0);  // 或 SpringApplication.exit()
}
```

**通知内容**：
- 操作人
- 变更的配置项列表
- 重启时间
- 重启原因（B 类配置变更）

**自重启失败处理**：
- 前置校验失败 → 用默认值 + warn 日志 + UI 横幅"部分配置无效"
- 应用启动失败 → 人工介入（看日志）

**运行期回写协议——三条硬约束（均有实测反证）**

1. **原地 setter 写入，禁止换引用**。`dbsyncer-common/src/main/java/org/dbsyncer/common/config/RetryConfig.java:68-70`
   的 `getGlobal()` 直接返回字段引用（不拷贝）；
   `dbsyncer-connector/dbsyncer-connector-sqlserver/src/main/java/org/dbsyncer/connector/sqlserver/ct/SqlServerCTListener.java:1228`
   在 `while`（:1229）**之前**取一次引用，整个 worker 线程生命周期反复使用（:1243）。
   → 任何"造一个新实例再替换"的方案（含 `AtomicReference` swap）会让长驻 worker 永远拿旧值：
   **UI 保存成功、日志显示已生效、实际参数永不变化**——正是本 ADR 要根除的假生效通道。
   反之原地写同一实例，对后续读取立即可见，不需锁、不需 `@RefreshScope`（全仓 0 处）。
   ⇒ 同时收紧方案 E：`Binder` 必绑到 **live 实例**（`retryConfig.getGlobal()`），不得新建后替换。
2. **有派生缓存的字段必须走 setter**。`RetryPolicy.java:120-123`（`setKeywords`）、`:138-142`（`setMatchMode`）
   会把 `volatile matcher`/`excludeMatcher`（`:47`）置 null，`:159-160` 懒重建。
   用反射 / `BeanUtils.copyProperties` 直写字段会绕过失效 → **改值不生效**。
3. **getter 不一定存在，回显要先补**。`CacheConfig` 的 `cache` 字段只有 setter
   （`dbsyncer-common/src/main/java/org/dbsyncer/common/config/CacheConfig.java:95`）、无 getter → 当前无法回显。

**为什么必须 refresh 前注入（F10）**：4 个线程池 `@Bean` 在 bean 创建期执行
（`GeneralBufferConfig:34`、`StorageConfig:38`、`DispatchTaskConfig:37`、`SchedulerConfig:30`），
而 `PreloadTemplate` 挂 `ContextRefreshedEvent`（`PreloadTemplate.java:49`、`:81`）**更晚**。
在其后回写 `GeneralBufferConfig.threadCoreSize` 毫无意义——池子早已按 properties 值建好。

**为什么是 sidecar 而不是 EPP 直读 DB（F13）**：`storage.type=disk` 时配置存在
**Lucene 索引**里（`DiskStorageService.java:55` `user.dir/data/`，查询走
`:65 select(...)` + `:200 BooleanClause`/`:208 Term`），启动期读它要引入整套 Lucene 读路径；
`storage.type=mysql` 时又要裸 JDBC。两条读法、两套 fail-soft，不值得。
sidecar 方案与存储类型**解耦**，EPP 只做"读一个 properties 文件"，文件不存在即回退 properties——
天然 fail-soft。DB 仍是唯一事实来源（UI 展示、审计、导出导入都走 DB），sidecar 是**可删的派生缓存**。

**L2 修订：启动期绝对禁止触碰 `getSystemConfig()`**：
迁移、对照表、启动校验三个钩子必须通过 `profileComponent.queryAll(SystemConfig.class)`
直接查存储层（或走 `OperationTemplate.queryAll`），**绝不**调用 `getSystemConfig()`——
后者在记录不存在时会触发 `checkAddConfigModel(new HashMap<>())` 创建默认配置并落库，
复活 ADR-0028 修掉的重复创建问题。单测锁定：启动期不调用 `getSystemConfig()`。

**sidecar 路径定义（L1）**：`{app.home}/config/dbsyncer-runtime.properties`，
其中 `app.home` = `System.getProperty("user.dir")` = 启动脚本中的 `$DBS_HOME`
（见 `startup.sh:46`、`startup.bat:22`、`startup-docker.sh:45` 的 `-Duser.dir=$DBS_HOME`）。
该目录已用于 `data/`（DiskStorageService:55）、`conf/`（SdkSupportConfiguration:36）、
`helpdocs/`（HelpDocController:52），sidecar 放 `config/` 子目录与之一致。

**`PreloadTemplate` 不需要修改**：注入发生在它之前，它与 ADR-0028 的启动门闸
（`StartupGate`、`PreloadTemplate:72`/`:94`/`:98-108`）约束完全解耦。
唯一硬约束：**任何新增读取都不得在 bean 构造期触碰 `getSystemConfig()`**（F14），
否则会复活 ADR-0028 修掉的重复创建问题。

**属性源命名（F12）**：`StorageSupportConfiguration:57-59` 按属性源**名称是否含 `application`**
决定是否收集，并在 `:71`/`:80` 无检查强转 `Map<String, OriginTrackedValue>`。
→ EPP 的 PropertySource 固定命名 `dbsyncerRuntimeConfig`（**不含 `application`**），单测锁定。
副作用是好事：该过滤恰好保证"配置存在哪"不会被 DB 里的配置决定（自举环安全）。

### 3. 为什么不在线重建线程池/缓冲区

| 风险 | 依据 |
|------|------|
| 队列容量与调度周期在建队时固化 | `AbstractBufferActuator:95 new LinkedBlockingQueue<>(capacity)`、`:87 start(taskKey, period, this)`（F11）。换引用会丢排队数据；安全搬迁需 暂停→排空→建新→回填→恢复，存在窗口期 |
| 注入引用无法替换 | 线程池经 `@Resource` 注入且无 setter，需 `volatile`+setter 侵入 6+ 个类 |
| `taskScheduler` 是全局定时枢纽 | 驱动所有 `ScheduledTaskJob`（缓冲区消费、指标上报、监控采集、增量拉取），重建需重注册全部任务 |
| 半生效更糟 | F11 实测：`pullCount`/`writerCount` 是热读（:263/:294），`queueCapacity` 不是（:224 读字段但队列已建）。在线改会得到"部分参数变了、部分没变"的状态 |
| 收益不对等 | B 类改动频率极低（部署后基本不动） |

> 因此缓冲区 Tab 的 8 项要**逐项标注生效级别**，不能整 Tab 一句"重启生效"糊过去：
> `buffer-pull-count`/`buffer-writer-count` 立即生效；`buffer-queue-capacity`/`buffer-period-millisecond`
> 需**重启任务**（不是重启应用，任务级 `stop/start` 即可，因为队列在 `start()` 时新建）。

### 4. UI 布局

系统参数页改为 6 Tab，每 Tab 独立保存：

| Tab | 内容 | 生效 | 通道 |
|-----|------|------|------|
| 1 基础设置 | 现有 10 字段（不动）+ 底部折叠 A 类只读 | 立即 | `POST /system/edit`（现有，`mapToBean`） |
| 2 执行器 | 4 个线程池共 10 项 | ⚠️ 重启应用 | `POST /system/editTab`（JSON） |
| 3 缓冲区 | general/storage 各 4 项 | ⚠️ 混合：2 项立即 / 2 项重启任务 | 同上 |
| 4 重试策略 | `RetryPolicy` 11 项 | 立即（任务级覆盖除外，L7） | 同上 |
| 5 通知通道 | channels + mail 3 + dingtalk 3 | 立即（`notify-types` 需先做 L8 修复） | 同上 |
| 6 错误处理 | threshold + fatal-match-mode + fatal-keywords | 立即 | 同上 |

**所有配置项必须带问号图标 + 悬浮提示**，逐条说明"作用 / 影响面 / 生效时机 / 取值边界 / 误配后果"。
这是本 ADR 的验收项之一（用户原始诉求），文案全文见设计稿 §6，且由 §4 的元数据单一来源驱动生成，
不允许在 HTML 里手抄。

## 影响

- **`dbsyncer-common`**：新增 12 个 Props 类（6 个 A 类 + 5 个 B/C 类 + BasicProps）+ Tab 元数据枚举（F19：唯一两侧可见的位置）。**不新增注解体系**——
  元数据（键名、生效级别、范围、提示文案）集中写在 `SystemTabEnum` 的项描述符里，单一来源同时驱动
  UI 渲染、校验、提示与 sidecar 键生成。
- **`dbsyncer-parser`**：`SystemConfig` 结构重构（根节点不留具体配置项，全部组织成子配置类），加 `schemaVersion` 字段。
- **`dbsyncer-biz`**：新增 `RuntimeConfigService`（读：按 Tab 合并 DB 子对象与 Bean 实际值；
  写：整块替换 + 回写 Bean + 重建 sidecar）。放 biz 的理由：需同时看到 `SystemConfig`(parser)
  与全部 B/C 目标 Bean(common/parser)，而 biz → manager → parser 依赖链已成立（`PreloadTemplate`
  即同时引用二者，F19）。**它看不到 `WebAppConfig`（在 web）**，因此 A 类只读值统一由 web 层
  直读 `Environment`（`environment.getProperty(...)`）而不读 Bean——避开模块方向问题，且 A 类
  本就未覆盖时等于 properties 值。
- **`dbsyncer-web`**：`SystemController` 加 3 个端点；`system.html` 85 行单表单 → 6 Tab；
  新增 `META-INF/spring.factories`（当前不存在，F19）注册 `EnvironmentPostProcessor`。
- **M3 修订：废除 `/system/edit` + `mapToBean` 通道**。Tab 1 迁到 `BasicProps` 子对象后
  `mapToBean` 无法处理嵌套路径（C2），继续保留只会造成两套保存通路并存的混乱。
  迁移策略：`schemaVersion>=1` 后前端不再调用 `/system/edit`，后端该端点标记 `@Deprecated`
  并返回 410 Gone + 提示前端升级。存量自动化脚本需迁移到 `/system/editTab` + `{tab:"basic"}`。
- **M1 修订：`editTab` 引入 synchronized 锁**。`SystemConfigServiceImpl` 的 `editTab`
  方法加 `synchronized`（与现有 `getSystemConfig()` 的双检锁同一把锁），防止两个 Tab
  并发保存时读-改-写丢失更新。锁粒度为实例级，足够（单例 Service）。
- **`dbsyncer-manager`**：`PreloadTemplate` 新增配置迁移逻辑（检测 `schemaVersion==0` 时从 bean 迁移到 DB）+ 启动期配置对照表打印。
- **前置修复（独立于本 ADR 亦应做）**：`MailConfig`/`DingTalkConfig.setNotifyTypes()` 补
  `notifyTypeSet = null`——`ErrorQueueConfig` 的同类 setter 已经是对的（F17c），属真实遗漏。
- **新增成本**：sidecar 的写入与失效逻辑（约 100 行，含并发写与原子替换）；配置迁移逻辑（约 50 行）；前置校验器（约 60 行）；自重启 + 发消息（约 30 行）。
- **时间影响**：预计 3.5 天。
