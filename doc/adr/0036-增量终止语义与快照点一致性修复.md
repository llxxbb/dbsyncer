## 背景

线上复现（本地 MySQL → 目标库，混合模式，熔断发生在**增量阶段**）：

1. 全量同步完成后，手动下线目标库连接
2. 源库插入 3 条数据
3. 第 1 条重试耗尽 → 入错误队列 → 熔断（阈值 1）→ 任务"终止"
4. 上线目标库连接，重启任务
5. **第 2、3 条永久丢失**；此后新增的第 4 条正常同步

日志证据（`logs/info.log`）：

```
15:46:39:743  熔断触发: metaId=1542828091976585216, 错误计数(1)达到熔断阈值(1)
15:46:40:164  熔断事件: 任务未运行, 无需关闭, mappingId=1542828091951419392   ← close 被跳过
15:46:40:166  任务已停止，跳过批次处理: metaId=..., 分区=test_converter_from    ← 第 2、3 条被丢弃
15:46:40:166  executeSync - INSERT, 2条, 1ms                                ← 紧接着提交快照点
15:57:12:877  MySQLExtractor is already started                             ← 重启是空操作
```

定位到四个缺陷：

| # | 缺陷 | 位置 |
|---|------|------|
| 1 | **熔断关闭被自己的守卫挡死**：`closeTask` 先置 `ERROR` 再发事件，监听器以 `!meta.isRunning()` 为判据 → 恒成立 → `managerFactory.close()` 永不执行。结果是"假终止"：binlog client 仍连接、执行器仍调度、`meta.getListener()` 仍非 null | `ErrorQueueCollectorImpl:247,254`、`CircuitBreakerEventListener:36` |
| 2 | **跳过的批次照样提交快照点**：`doSync` 在非运行态直接 return（数据既没写、也没进错误队列），`executeBatch` 仍无条件 `commitOffset` → `refreshEvent` → 3s 内落库，快照点越过未落库数据 | `MetaBufferActuator:334,362,554` |
| 3 | **重启变成空操作**：listener 未释放 → `IncrementPuller` 复用旧实例（并跳过 `tableGroupContext.put()`）→ `MySQLListener.start()` 发现已连接只打一行日志就 return，从**实时位置**而非快照点续读 | `IncrementPuller:120-131`、`MySQLListener:68-70` |
| 4 | **已关闭的监听器仍能写快照**：`close()` 只写日志；`flushExecutor` 仅在 `@PreDestroy destroy()` 中关闭，而 listener 由 `connectorFactory.getListener()` 反射创建、不是 Spring Bean，`destroy()` 永不触发 | `AbstractListener:146,258` |

缺陷 2 还有第二条推进路径：`MySQLListener:276` 的 XID 快路径在 `hasPendingTaskData()==false` 时直接 `refreshEvent`；执行器 `unbind` 后该判断恒为 false，只要旧 client 未断开，源库**任意无关事务**都会把快照点推到实时位置。

## 决策

**核心不变量**：`持久化快照点 ≤ 最后一条成功写入目标库（或已进入错误队列）的数据位置`。被跳过、被丢弃的批次**不得**推进快照点。

**与 ADR-0023 的边界**：ADR-0023 决策 10 已确定"写入重试耗尽 → 进错误队列 → 批次正常返回、offset 前进"，因为错误队列可重试恢复。本 ADR 不改变该语义，只堵住"既没写、也没进错误队列"的静默跳过路径。

修正后增量同步语义为**至少一次**（重放幂等性见"影响"）。

### 决策 1：熔断关闭判据从"运行状态"改为"资源绑定"

`CircuitBreakerEventListener` 不再以 `meta.isRunning()` 判断是否需要关闭 —— 事件到达前 `closeTask` 必已置 `ERROR`，该判据恒假。改为：

- **判据**：`meta.getListener() != null`（增量资源仍绑定）才执行 `managerFactory.close(mapping)`
- **幂等**：per-mappingId 的并发 Set 做 CAS 守卫，并发熔断只关闭一次，`finally` 释放
- **异步**：关闭动作交由 `CompletableFuture.runAsync` 执行，与 `ParserConsumer.errorEvent` 已验证可用的关闭路径保持一致

**理由**：状态表达"意图"，资源表达"事实"；释放动作必须由事实驱动，否则守卫会把唯一一次关闭机会吃掉。

**为何异步**：`CircuitBreakEvent` 由执行器出队线程同步发布（`handleFailData → closeTask → publishEvent`），就地关闭有两个副作用：① `client.disconnect()` 的 join 与快照补写会把提交偏移量的线程阻塞数秒，拉长丢失窗口；② `unbind → ScheduledTaskService.stop → future.cancel(true)` 会对**正在运行的任务**发起中断，在出队线程上执行等于自我中断，中断标志会带进后续的存储写入。异步化后两者都消失，且 Meta 已在 `closeTask` 中同步置为 ERROR，决策 2 的出队守卫在此期间已生效，不依赖关闭完成。

### 决策 2：批次未落库不提交快照点

- `doSync()` 返回 `boolean`：非运行态跳过时返回 `false`，其余（含写入失败已进错误队列）返回 `true`
- `executeSync()` 透传该结果
- `executeBatch()` 仅在**全部表组都已处理**时 `commitOffset`；否则 WARN 并放弃提交
- `dequeue()` 每轮出队前检查 `isRunning()`，非运行态立即停止出队，残留事件留在队列、快照点不动

**理由**：`commitOffset` 原注释只论证了 FIFO 的**顺序**安全（"队列中事件位置 ≥ 当前批次最大位置"），未论证**落库成功**；把"已出队"当成"已写入"是本缺陷的直接根源。

### 决策 3：队列残留直接丢弃，不入错误队列

`MetaBufferActuator.stop()` 清空队列并 WARN 输出丢弃条数。

**理由**：决策 2 已保证快照点未越过这些事件，重启后监听器从快照点重连、源库自然重放；写错误队列会带来高昂的人工恢复成本，且与重放语义重复。

**约束**：丢弃必须留痕（WARN + 条数 + metaId），禁止静默。

### 决策 4：重启必须是真重启

- `IncrementPuller.start()` 移除"复用残留 listener"分支：检测到残留先 `close()` + `unbind()`，再按 `meta.getSnapshot()` 重建监听器
- `MySQLListener.start()` 遇到已连接不再静默 return：WARN 后 `disconnect()` 再按快照点重连

**理由**：复用旧实例既跳过 `tableGroupContext.put()`（后续 `pickers` 为空直接抛错），又让续读点脱离持久化快照，属于"假启动"。

### 决策 5：监听器关闭即冻结快照

`AbstractListener` 新增幂等的 `stopSnapshotFlush()`：置 `closed` → 同步补写一次 `pendingSnapshot` → 清空 `pendingSnapshot` → 关闭 `flushExecutor`。

- `close()` 调用它；各子类 `close()` **第一行**调用它，再执行阻塞式断开（消除断开窗口内到达的事件推进快照）
- `refreshEvent()` 在 `closed` 后 no-op（WARN）
- `destroy()`（`@PreDestroy`）复用同一方法，兑现其"系统关闭时立即持久化最新快照点"的既有注释
- `ParserConsumer.flushEvent()` 增加兜底：`meta.getListener() == null` 时丢弃写入

**理由**：listener 不是 Spring Bean，`@PreDestroy` 永不触发；已关闭的监听器继续写快照会覆盖新监听器的续读点。

### 决策 6：close 保留异常状态

`MappingModelService.resetMetaState()` 增加 `meta.isError()` 判断，与 `IncrementPuller.close()` 既有写法对齐。

**理由**：混合模式的关闭链路是 `ManagerFactory.close → getPuller(mapping.getModel()) → FullIncrementPuller.close → fullPuller.close → resetMetaState`，按**静态 model** 分派、与当前运行阶段无关。决策 1 生效后 close 真正执行，若无本项，熔断原因会被从"异常(3)"抹成"未运行(0)"，用户无法得知任务为何停止。

## 影响

- **技术影响**
  - **语义变更**：增量同步由"至多一次"变为**至少一次**。重启后可能重放"未提交批次 + ≤ 一个快照持久化周期（3s）"的数据。MySQL 目标端 `INSERT ... ON DUPLICATE KEY UPDATE`（`MySQLTemplate:49`）、PostgreSQL `ON CONFLICT DO UPDATE`（`PostgreSQLTemplate:84`）幂等；SqlServer 目标端为普通 INSERT，重放可能主键冲突并进错误队列（与既有崩溃恢复行为一致）。
  - 关闭时补写一次快照后冻结，不再出现"关闭后快照继续前进"。
  - 熔断后资源确定释放：binlog 连接、执行器调度、`tableGroupContext` 缓存。
  - 不涉及存储 schema、配置项、对外 HTTP 接口变更。
- **团队影响**：无。
- **时间影响**：单次迭代内完成。
