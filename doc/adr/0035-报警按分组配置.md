## 背景

当前报警/通知体系为**全局统一配置**：

```
调用方 → MessageService → CompositeNotifyService → 全局 NotifyProps（唯一）
                                                       ↑
                                          ConfigRegistry.getConfig().getNotify()
```

- `NotifyProps`（channels / mail / dingtalk）存储在 `SystemConfig` 中，全局唯一
- 所有 Mapping 的报警都走同一套通道、同一套接收人

**问题**：不同业务分组（ProjectGroup）的报警接收人、通知通道可能不同。例如：
- 分组 A（订单系统）→ 钉钉群 A + 邮箱 a@company.com
- 分组 B（财务系统）→ 钉钉群 B + 邮箱 b@company.com
- 未分组 → 走全局默认配置

## 决策

### 核心思路

**职责分离 + 按通道逐项覆盖 + 全局兜底**：

```
调用方（需要分组感知时）
  → NotifyConfigResolver.resolve(mappingId)  ← 配置解析（业务逻辑）
    → 解析 mappingId → projectGroupId（或 __unassigned__）
      → 该分组有覆盖某通道？ → 用分组的
      → 该通道未覆盖？ → 用全局 SystemConfig.notify 对应通道
  → CompositeNotifyService.sendMessage(msg, resolvedProps)  ← 发送（通知服务）

调用方（不需要分组感知时）
  → MessageService.sendMessage(title, content, type)  ← 走全局配置
    → CompositeNotifyService.sendMessage(msg)
```

**为什么不让 MessageService 处理分组**：
- `MessageService` 的职责是"发消息"，不是"决定用哪套配置发消息"
- 配置解析是业务逻辑，应该由业务层或专门的解析服务负责
- 让通知服务知道 mapping 属于哪个分组，是职责越界

### 数据模型

**SystemConfig 扩展**（ProjectGroup 不变）：

```java
public class SystemConfig extends ConfigModel {
    // 已有：全局默认通知配置
    private NotifyProps notify;

    // 新增：分组通知配置 Map
    //   key = projectGroupId  → 该分组的独立配置
    //   key = "__unassigned__" → 未分配分组的独立配置
    private Map<String, NotifyProps> groupNotifyConfigs;
}
```

**为什么不存 ProjectGroup**：
- 通知配置是"系统级"报警路由策略，不是分组自身属性
- UI 在"系统参数 → 通知通道"中管理，与全局配置同页
- "未分配"不属于任何 ProjectGroup，需要统一存储位置

### 覆盖策略：按通道逐项覆盖

分组可以只覆盖部分通道，未覆盖的通道走全局：

```
分组 A 只配了 dingtalk.webhook
  → 钉钉走分组 A 配置
  → 邮件走全局配置

分组 B 不启用任何自定义
  → 全部走全局配置
```

**合并逻辑**（伪代码）：

```java
resolveNotifyProps(mappingId):
  groupProps = lookupGroupProps(mappingId)  // 可能为 null
  globalProps = configRegistry.getConfig().getNotify()

  if (groupProps == null):
      return globalProps

  // 按通道逐项合并
  resolved = new NotifyProps()
  resolved.channels = merge(groupProps.channels, globalProps.channels)
  resolved.mail = (groupProps.mail != null) ? groupProps.mail : globalProps.mail
  resolved.dingtalk = (groupProps.dingtalk != null) ? groupProps.dingtalk : globalProps.dingtalk
  return resolved
```

### 配置解析服务

**新增 `NotifyConfigResolver` 接口**（parser 层）：

```java
/**
 * 通知配置解析器
 * <p>
 * 根据 mappingId 解析对应的通知配置（分组配置 + 全局兜底）
 */
public interface NotifyConfigResolver {
    /**
     * 解析通知配置
     *
     * @param mappingId 映射 ID，为 null 时返回全局配置
     * @return 通知配置
     */
    NotifyProps resolve(String mappingId);
}
```

**实现类**（parser 层）：

```java
@Component
public class NotifyConfigResolverImpl implements NotifyConfigResolver {
    @Resource
    private ConfigRegistry configRegistry;
    
    @Resource
    private ProfileComponent profileComponent;

    @Override
    public NotifyProps resolve(String mappingId) {
        NotifyProps globalProps = configRegistry.getConfig().getNotify();
        if (globalProps == null) {
            return null;
        }

        Map<String, NotifyProps> groupConfigs = configRegistry.getConfig().getGroupNotifyConfigs();
        if (groupConfigs == null || groupConfigs.isEmpty()) {
            return globalProps;
        }

        // 确定 key
        String key = ConfigConstant.UNASSIGNED_GROUP_KEY;
        if (StringUtil.isNotBlank(mappingId)) {
            String groupId = profileComponent.findProjectGroupId(mappingId);
            if (StringUtil.isNotBlank(groupId)) {
                key = groupId;
            }
        }

        NotifyProps groupProps = groupConfigs.get(key);
        if (groupProps == null) {
            return globalProps;
        }

        // 按通道合并
        return mergeNotifyProps(groupProps, globalProps);
    }

    private NotifyProps mergeNotifyProps(NotifyProps group, NotifyProps global) {
        NotifyProps merged = new NotifyProps();
        merged.setChannels(group.getChannels() != null ? group.getChannels() : global.getChannels());
        merged.setMail(group.getMail() != null ? group.getMail() : global.getMail());
        merged.setDingtalk(group.getDingtalk() != null ? group.getDingtalk() : global.getDingtalk());
        return merged;
    }
}
```

**ProfileComponent 扩展**（parser 层）：

```java
public interface ProfileComponent {
    // 已有
    List<ProjectGroup> getProjectGroupAll();
    
    // 新增：查找 mappingId 所属的分组 ID
    String findProjectGroupId(String mappingId);
}
```

### 接口变更

**MessageService（SDK 层）保持不变**：

```java
public interface MessageService {
    // 已有（保持不变，走全局配置）
    void sendMessage(String title, String content);
    void sendMessage(String title, String content, NotifyType type);
    
    // 不新增带 mappingId 的重载
}
```

**CompositeNotifyService 新增方法**：

```java
public void sendMessage(NotifyMessage msg, NotifyProps props) {
    // 用传入 props 替代 configRegistry.getConfig().getNotify()
}
```

**NotifyService 接口扩展**：

```java
public interface NotifyService {
    void sendMessage(NotifyMessage notifyMessage);
    
    // 新增：使用显式配置发送（default 方法，向后兼容）
    default void sendMessage(NotifyMessage notifyMessage, NotifyProps props) {
        if (props == null) return;
        sendMessage(notifyMessage);
    }
}
```

### 调用方改造

**需要分组感知的调用方**（直接调用 CompositeNotifyService）：

| 调用方 | 改造方式 |
|--------|---------|
| `ErrorQueueCollectorImpl.notifyError()` | 注入 `NotifyConfigResolver`，解析配置后调用 `compositeNotifyService.sendMessage(msg, props)` |
| `ParserConsumer` | 同上 |
| `MappingServiceImpl` | 同上 |
| `ConnectorFactory` DDL | 同上 |
| `RetryCallbacks` | 同上 |
| `ManagerFactory` | 同上 |
| `TableGroupServiceImpl` | 同上 |

**改造示例**：

```java
// 改造前
messageService.sendMessage("dbsyncer", msg.toString(), NotifyType.TASK_INTERRUPTED);

// 改造后
NotifyProps props = notifyConfigResolver.resolve(mappingId);
NotifyMessage notifyMsg = NotifyMessage.newBuilder()
    .setTitle("dbsyncer")
    .setContent(msg.toString())
    .setType(NotifyType.TASK_INTERRUPTED)
    .setReceivers(getReceivers())
    .build();
compositeNotifyService.sendMessage(notifyMsg, props);
```

**不需要分组感知的调用方**：
- 继续使用 `MessageService.sendMessage(title, content, type)`，走全局配置

### 分组 → Mapping 反向索引

当前 `ProjectGroup` 持有 `mappingIds` 列表，但没有反向索引。

**方案**：在 `ProfileComponent` 中增加方法，按需遍历（分组数量少，通常 < 50）：

```java
// ProfileComponent 新增
String findProjectGroupId(String mappingId);
```

**为什么不放在 ProjectGroupService**：
- `ProjectGroupService` 在 biz 层，`NotifyConfigResolver` 在 parser 层
- parser 层不能依赖 biz 层（会造成循环依赖）
- `ProfileComponent` 在 parser 层，已有 `getProjectGroupAll()`，职责匹配

如果后续分组数量增长，可加缓存 `Map<String, String>`（mappingId → projectGroupId），在分组变更时失效。当前阶段线性扫描足够。

### UI 设计

在"系统参数 → 通知通道"Tab 中，全局配置下方新增**分组通知配置**区域，采用 Master-Detail 布局：

```
┌─ 系统参数 → 通知通道 ──────────────────────────────────────────┐
│                                                                  │
│  ═══ 全局默认配置 ═══                                            │
│  启用通道: ☑ 邮件  ☑ 钉钉                                       │
│  邮件/钉钉详细配置 ...                                            │
│  [保存] [恢复系统默认]                                            │
│                                                                  │
│  ═══ 分组配置 ═══  未配置自定义的分组使用上方全局默认配置          │
│  ┌──────────────────┬───────────────────────────────────────────┐│
│  │ [全部][已配][未配]│  分组名: 订单系统                         ││
│  │ ─────────────── │  状态: ● 已有独立配置                      ││
│  │ 订单系统    ●    │                                           ││
│  │ 财务系统    ○    │  ☑ 启用自定义配置                          ││
│  │ 用户系统    ○    │  ─────────────────────────────             ││
│  │ ─────────────── │  启用通道: ☑ 邮件  ☐ 钉钉                  ││
│  │ 未分配      ○    │  邮件配置: ...                             ││
│  │                  │  钉钉配置: ...                             ││
│  │                  │                                           ││
│  │                  │  [测试发送]  [保存]  [清除配置]             ││
│  └──────────────────┴───────────────────────────────────────────┘│
└──────────────────────────────────────────────────────────────────┘
```

**左侧列表**：
- 每项显示：分组名 + 配置状态（● 有独立配置 / ○ 走全局）
- 支持按配置状态排序/过滤：全部 / 已配置 / 未配置
- 末尾固定"未分配"项，覆盖未归入任何 ProjectGroup 的 Mapping

**右侧详情**：
- 选中分组后展示配置表单
- "清除配置"= 删除该分组的独立配置，回退到全局
- "测试发送"= 用当前配置发一条测试消息，验证有效性

## 影响范围

### 模块影响

| 模块 | 变更 |
|------|------|
| `dbsyncer-common` | `SystemConfig` 加 `groupNotifyConfigs` 字段 |
| `dbsyncer-parser` | 新增 `NotifyConfigResolver` 接口和实现；`ProfileComponent` 加 `findProjectGroupId()` |
| `dbsyncer-sdk` | `NotifyService` 接口加 `default sendMessage(msg, props)` |
| `dbsyncer-biz` | 调用方改造（注入 `NotifyConfigResolver`） |
| `dbsyncer-web` | "系统参数 → 通知通道"Tab 增加分组配置区域 |

### 兼容性

- **向后兼容**：`groupNotifyConfigs` 为 null/空 Map 时行为与当前完全一致
- **已有调用**：`MessageService` 接口不变，走全局配置
- **存储兼容**：SystemConfig JSON 新增可选字段，旧数据反序列化时 groupNotifyConfigs = null
- **ProjectGroup 不变**：模型零改动

## 风险

| 风险 | 应对 |
|------|------|
| 分组配置错误导致报警丢失 | UI 上提供"测试发送"按钮；分组配置为空通道时 warn 日志 |
| 全局配置变更后分组不感知 | 分组走全局兜底时，实时读取 ConfigRegistry，无缓存问题 |
| 调用方改造遗漏 | 保留 `MessageService` 无 mappingId 重载，走全局；逐步迁移 |
| 分组/映射关系变更 | `findProjectGroupId()` 每次实时扫描，无缓存一致性问题 |
