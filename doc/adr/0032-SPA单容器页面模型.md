## 背景

Web 端是 hash 路由的 SPA：外壳 `public/index.html` 加载全部公共库，`public/content.html` 提供内容容器，`public/nav.html` 的菜单项带 `data-route` 指定目标容器。基线声明了 `initContainer0`~`initContainer6` 共 7 个容器。

在 `650ee1aa`（统一任务列表）之后陆续暴露三个现象：

1. 「任务」页列表不跟随 `projectGroupId` 变化，卡片视图正常；
2. 鼠标在分组列表上移动就持续发送网络请求；
3. 仅切到「数据源」再切回「异常任务」，异常任务列表变空。

排查发现三者同源于 **route/多容器模型**，且该模型自身还埋着若干独立缺陷：

| 缺陷 | 表现 |
|------|------|
| `handleHashChange` 的 route 解析恒为 0 | `hashPath.split('?')` 先丢掉分隔符，再对裸串 `route=1` 套用 `/[?&]route=(\d+)/`，永远不匹配 → 所有页面都塞进 `initContainer0`，并发 `.load()` 互相覆盖 DOM |
| `doLoader` 与 `hashchange` 双重加载 | `doLoader` 自己 `.load()` 一次，`updateHash` 又触发 `hashchange → doLoaderWithoutHashUpdate` 再加载一次 → 页面脚本执行两遍、定时器与请求翻倍 |
| `datasource.html` 是完整独立页面 | 它自带 CDN 版 jQuery/Bootstrap/loading-plus/common.js。作为片段注入后，**跨域 CDN jQuery 异步下载完成时覆盖 `window.$`**，抹掉外壳注册的全部插件（`$.loadingT`、`$.fn.serializeJson`、`$.fn.tableDnD` 变为 `undefined`）→ 其它页面脚本首行即抛异常、列表渲染为空。因同域脚本走 `async:false` 抢先注册到旧 jQuery 上，该故障**依赖时序**，时好时坏 |
| 页面定时器无人回收 | 句柄存在模块级/全局变量中，导航离开后继续轮询；补救办法是往**常驻的** `window` 和外壳导航按钮上绑 `beforeunload`/`hashchange`/`click`，每次进入页面多叠一层处理器，而全局句柄被新实例覆盖后旧定时器永远清不掉 |

其中第 1、2 条使「同一容器被并发写入」，第 3 条使「页面脚本运行时能力被摧毁」，第 4 条使「离开页面后仍在发请求」——现象 2 和现象 3 分别是第 4 条与第 3 条的直接结果。

## 决策

**采用单容器页面模型 + 页面代际守卫**：全站只有一个内容容器，每次导航用新页面的完整 HTML 覆盖它；页面之间不共享任何状态，旧页面的异步回调靠代际号自动失效。

1. **删除 route 概念**。`content.html` 只保留 `<div id="initContainer" th:fragment="content">`；`nav.html` 去掉全部 `data-route`；`updateHash` / `doLoader` / `doLoaderWithoutHashUpdate` 去掉 `route` 参数；`handleHashChange` 不再解析任何路由编号（URL 即页面标识）。

2. **确立片段不变式**：公共库只允许外壳引入，内容片段只带自己的 CSS 与页面 JS。`datasource.html` 重写为裸片段（根元素 `<div id="datasourcePage" th:fragment="page">`），删除 DOCTYPE/head/body/wrapper/`#nav` 与 6 处库重引入，并在文件内留下禁止再次引入的注释。

3. **加载器只加载一次**。`updateHash(url)` 返回哈希是否真的变化；`doLoader(url)` 在哈希变化时直接返回，把加载交给 `hashchange` 路径。`doLoaderWithoutHashUpdate(url)` 用 `$.ajax({dataType:'html'})` + `$initContainer.html(html)` 取代 jQuery `.load()`，并在发起前**中断上一个容器请求**（`containerXHR.abort()`）、**递增 `window.__pageEpoch`**。

4. **页面自我销毁**。`common.js` 提供 `pageGuard()` / `isPageAlive(guard)`。持有定时器的页面在启动时取一次代际号，每个定时器与 AJAX 回调开头比对：不符则 `clearInterval` 自己的句柄并返回。定时器句柄一律**局部持有**，不用顶层 `var`。

5. **守卫按需使用**。只有持有定时器的页面需要守卫；`datasource.js` 无定时器，其迟到回调只会写入已脱离文档的节点（jQuery 对空集合静默无操作），保持基线不动，避免投机性样板。

顺带修正的两个页面级缺陷（与本模型无耦合，但同批发现）：

- `index/index.js` 的 `init()` 改为读服务端渲染的 `$('#projectGroup').val()`，不再解析地址栏（hash 路由下常规 query 解析取不到 `#` 之后的参数，这是列表不跟随分组的直接原因）；
- `public/index/index.html` 删除覆盖在分组项上的两个透明全尺寸 `onclick="groupShow(...)"` 按钮（与 `bindGroupList()` 的委托处理器重复触发，一次点击发两次 `updateHash`），改为在样式上直接给 `cursor: pointer`，并把右侧下拉容器的 `z-index` 提到 2；`groupShow()` 不再额外调用 `loadTaskList()`。

### 备选方案与否决理由

| 方案 | 否决理由 |
|------|---------|
| 只修 route 解析，保留 7 容器 | 改动最小，但双重加载、跨页残留状态、插件被覆盖三类问题都与 route 正确性无关，仍需各自打补丁；且每个新页面都要分配稳定 route 编号 |
| `common.js` 维护页面清理函数注册表（`registerPageCleanup`） | `common.js` 反向耦合具体页面；新增页面忘记注册即静默泄漏，是隐式契约 |
| 加载遮罩引用计数 + 强制关闭 | 治标：`.load()` 回调里那次不成对的 `$.loadingT(false)` 本是「不自管理遮罩的页面」唯一的关闭时机，计数无法解决插件被抹掉的根因 |
| 过期响应序号表（`containerLoadSeq`） | 被「中断上一个 XHR + 代际号」取代：一个变量替代一张 map |

## 影响

- **技术影响**：
  - 页面互相干扰在结构上被消除（单容器整体覆盖 + 代际失效）；
  - 每次导航对片段的请求从 2 次降为 1 次，页面脚本只执行一遍；
  - 反复进出页面不再累积定时器与 `window`/外壳事件处理器；
  - 删除约 150 行补偿机制（清理注册表、序号表、遮罩计数、`pendingXHR` 样板），`static/plugins/js/loading-plus/loading-plus.js` 恢复为与上游字节一致；
  - 代价：页面状态一律不跨导航保留（这是本模型的**设计前提**，非缺陷）；`datasource.css` 的 `<link>` 与 `index/index.html` 的内联 `<style>` 会在每次进入时重复追加（可接受，量级极小）。
- **团队影响**：新增页面须遵守两条规则——① 片段内不得引入任何公共库；② 创建定时器就必须 `pageGuard()` + `isPageAlive()` 自我销毁。两条规则均已写入相应文件的注释。
- **时间影响**：涉及 4 个模板与 6 个 JS 文件，含 Playwright 端到端验证，1 天完成。
- **兼容性**：历史哈希或 `sessionStorage.previousPage` 中仍带 `route=N` 的值不做剥离——服务端忽略该未知参数，`handleHashChange` 也无需再保留遗留解析逻辑。
