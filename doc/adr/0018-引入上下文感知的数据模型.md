# ADR 0018: 引入上下文感知的数据模型 (Context-Aware Data Model)

## Status
**Proposed**

## Context
当前的同步流程中，数据流转采用 `List<Map<String, Object>>`。在 `writer` 端（尤其是 Kafka、Elasticsearch、SQL Server 等），需要频繁从 `PluginContext` 或 `TableGroup` 中查询元数据来确定主键字段、目标表名等。

这导致了：
1. **高频计算开销**：即使是 O(1) 的查询，在每秒处理数万数据的情况下，重复操作也会消耗 CPU 周期。
2. **代码逻辑耦合**：Connector 必须了解如何从 `PluginContext` 中组合出主键，导致逻辑分散。
3. **扩展性差**：无法优雅支持“一任务多表”同步（异构数据流）。

## Decision
**引入 `SyncRow` 包装对象，将原始数据与对应的上下文引用捆绑在一起。**

### 核心模型：
```java
public record SyncRow(
    Map<String, Object> data,      // 原始同步数据
    PluginContext context           // 包含主键、表名、插件配置等所有元数据的上下文
) {}
```

### 核心变动点：
1. **Parser 层预绑定**：
   在 `ParserComponentImpl` 完成字段映射和转换后，立即将 `List<Map>` 转换为 `List<SyncRow>`。
2. **Connector 层直接消费**：
   `AbstractDatabaseConnector` 的写入接口改为接收 `List<SyncRow>`，Connector 直接从 `SyncRow` 中提取所需元数据。

### 收益：
- **极致性能**：消除每条数据都要在 `PluginContext` 中重复查询逻辑的开销。
- **高度解耦**：Connector 变得更加纯粹，仅负责根据 `SyncRow` 提供的上下文执行写入。
- **内存最优**：由于 `PluginContext` 在整个批次中是单例引用的，`SyncRow` 只增加了一个引用指针的开销，内存占用极低。

## Consequences
- **接口变更**：需要更新 `AbstractConnector` 及其子类所有涉及写入/更新/删除的接口。
- **Parser 修改**：需要在数据流出 Parser 前完成 `SyncRow` 的构建。

## Implementation Plan
1. 在 `dbsyncer-sdk` 中定义 `SyncRow`。
2. 更新 `AbstractConnector` 及其子类的写入/删除/更新/UPSERT 接口。
3. 修改 `ParserComponentImpl` 在数据转换后封装 `SyncRow`。
4. 更新 `AbstractDatabaseConnector` 实现类，从 `SyncRow` 中提取主键和元数据。
5. 验证高并发场景下的内存占用和写入性能。
