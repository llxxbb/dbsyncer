# ADR-0023: 错误队列数据一致性修复

## 背景

当前错误队列处理存在以下问题：

1. **处理逻辑分裂**：全量同步 (`flushFullData`) 和增量同步 (`flushIncrementData`) 使用不同的错误处理路径，增量有通知而全量没有，逻辑不一致。

2. **Result 传导链过长**：错误数据通过 `Result` 对象从 `MetaBufferActuator` → `FlushStrategyImpl` 层层传递，中间环节多，容易遗漏或出错。

3. **无熔断机制**：即使错误持续累积，任务也不会自动停止，可能导致大量无效同步和资源浪费。

4. **计数可能漂移**：`Meta.fail` 是内存值，与 `dbsyncer_data` 表中 `success=0` 的实际行数可能不一致（如异常重启、写入失败等场景）。

5. **错误数据格式不一致**：`ConnectorFactory` 和非数据库连接器（ES/Kafka/File）在错误时使用 `SyncRow.getData()`（目标格式）构造 `failData`，而增量路径使用源格式。重试机制期望源格式数据，导致字段名不匹配时重试失败。

6. **全量同步错误数据丢失**：`writeBatch` 抛异常时直接向上抛出，错误数据完全丢失，无法重试。

7. **部分行失败静默丢弃**：批量执行中 `execute[i] != 1` 的行既未加入 `successData` 也未加入 `failData`，数据丢失。

## 决策

### 决策 1：新增独立错误队列服务

形成 `ErrorQueueService` 独立服务，统一全量/增量的错误写入、计数更新、通知发送逻辑（DML/DDL 双入口，见决策 11）。

**理由**：消除全量/增量的处理差异，提供单一职责的错误处理入口。

### 决策 2：现场处理，去除 Result 传导链

遇到无法同步的数据，在错误发生点（`MetaBufferActuator`、`FullSyncExecutorImpl`）直接调用 `ErrorQueueService` 处理，不再经由 `Result` 回传。

**边界澄清**：`Result` 是 `ConnectorService` 接口契约，予以保留。`ConnectorFactory` 仅负责两件事：
1. 写入异常时统一提取 `SyncRow.getSourceData()` 填充 `Result.failData`（源格式）
2. 整批自动重试（见决策 10）

被去除的是 `Result → FlushStrategyImpl` 这条错误处理链：错误写入、计数、通知不再经过该链路。

**理由**：简化错误处理流程，杜绝中间环节遗漏，同时保持 connector 接口稳定。

### 决策 3：错误阈值熔断

错误计数累计到阈值时终止任务执行，并发送通知。

- 配置项：`dbsyncer.error.threshold`（默认 0 = 不启用）
  - 同时移除现有死配置 `dbsyncer.error.fence.enable` / `dbsyncer.error.fence.max-size`（无实现引用，与 threshold 职责重复）
- 触发条件：`Meta.fail >= threshold`（全量/增量统一计入）
- 停止机制：
  1. `ErrorQueueService` 将 Meta 置为 `ERROR`（errorMessage 注明熔断原因）并持久化
  2. 发布 Spring 事件 `CircuitBreakEvent`（携带 mappingId），biz 层监听并调用 `managerFactory.close(mapping)` 完成 listener 关闭与资源清理
  3. 发送熔断通知（`NotifyType.DATA_ERROR_CIRCUIT_BREAKER`）
  - 全量同步无需主动中断：`FullSyncExecutorImpl` 每批次循环检查 `meta.isRunning()`，状态变更后自然退出
- 恢复：手动重启任务

**理由**：以未解决的错误数（fail 累计，重试成功递减）为口径，全量/增量统一，避免大量无效同步和资源浪费。

### 决策 4：计数对齐功能

在"错误队列"面板中提供"计数对齐"按钮，以存储中实际失败行数为准修正计数。

- 位置：`/mapping/page/edit` 页面，"错误队列"面板，"清空数据"按钮前
- 行为：
  1. 遍历该 meta 下所有 TableGroup，逐个查询存储中 `success=0` 且 `tableGroupId=xx` 的行数（复用 `StorageService.query().getTotal()`，不新增存储接口）
  2. 更新各 `TableGroup.fail`，`Meta.fail = Σ`（total 不对齐，关注异常口径）
  3. 记录漂移日志，前端刷新页面

**理由**：Meta/TableGroup 的 fail 为内存值，与存储实际行数可能不一致；对齐粒度下沉到表组，修正更精确。

### 决策 5：重试减计数完善

手工重试成功后，通过 `ErrorQueueService.onRetrySuccess()` 统一调用 `CounterService.decrementFail()` 原子减去失败计数。

**理由**：现有逻辑已实现，纳入统一管理并原子化。

### 决策 6：SyncRow 携带源数据（限定 DML）

扩展 `SyncRow` 类，新增 `sourceData` 字段，存储源格式原始数据。Picker 创建 SyncRow 时直接引用源数据（不深拷贝，避免正常路径内存开销）。DML 错误路径统一使用 `SyncRow.getSourceData()` 构造 `failData`；DDL 错误独立处理（见决策 11）。

**理由**：
- 错误队列存储原始现场数据，重试时重新走完整管道（映射 → 转换 → 写入），保证一致性
- 消除各错误路径数据格式不一致问题
- 全量同步路径也能捕获错误数据

### 决策 7：部分行失败捕获

批量执行中 `execute[i] != 1 && execute[i] != -2` 的行加入 `failData`，使用 `SyncRow.getSourceData()`（`-2` 即 `SUCCESS_NO_INFO`，维持成功语义）。

**理由**：杜绝数据丢失，确保每条失败记录都能被重试。

### 决策 8：引入 CounterService 统一管理计数

新增 `CounterService` 服务，统一管理 `Meta.fail/success`、`TableGroup.fail/success` 及细分字段（full/increment）的更新。

- 方法：`incrementSuccess(Meta, TableGroup, count)`、`incrementFail(...)`、`decrementFail(...)`，签名不区分全量/增量
- 阶段区分：内部读取 `meta.getSyncPhase()`（`FULL` / `INCREMENTAL`）判定细分字段归属，聚合字段与细分字段一次维护，并同步 `TableGroup.status`
- 原子性：内部按 meta 加锁（`synchronized`）累加，不改 Meta 字段类型，避免破坏 JSON 序列化
- 刷新：调用方在关键节点手动调用 `flush()` 提交到 DB（全量同步快照点、增量同步偏移量刷新、重试成功后）

**理由**：
- 消除散落在多处的计数更新逻辑，保证聚合与细分字段一致
- 修复并发计数丢失更新的隐患（现状 `setFail(getFail() + n)` 非原子）
- 批量提交减少 DB 写入次数

### 决策 9：Picker 方法合并

合并 `Picker` 中两个 `pickTargetData` 方法，提取核心逻辑到私有方法 `pickTargetDataFromMaps()`，统一设置 `sourceData`（直接引用源 Map），并移除 `sourceMapList` 输出参数（writeBatch 异常时改用 `target.stream().map(SyncRow::getSourceData)` 提取）。

**理由**：
- 消除重复的 `exchange()` + 创建 `SyncRow` 逻辑
- 统一错误处理和数据过滤
- 消除冗余输出参数，`SyncRow.sourceData` 已能承载源数据

### 决策 10：统一自动重试机制

将自动重试从 `AbstractDatabaseConnector` 提升到 `ConnectorFactory.writeBatch()` 层面，所有连接器（数据库/非数据库）统一享受自动重试。

- 非数据库连接器（ES/File/Kafka）改造：移除内部 try-catch 与 `addFailData`，整体异常（含 ES bulk 部分 item 失败）直接抛出，交由 `ConnectorFactory` 统一重试
- 重试失败后：抛异常 → 上游（`MetaBufferActuator` / `FullSyncExecutorImpl`）catch → `ErrorQueueService.handleFailData()` 进错误队列（源格式），批次正常返回、offset 前进，与数据库路径完全统一
- `AbstractDatabaseConnector` 移除内部 retryInterceptor

**理由**：
- 降低维护成本，统一错误处理逻辑
- 非数据库连接器也可能有瞬时错误（如 Kafka 临时不可用）
- 简化连接器实现，符合"现场处理"原则

### 决策 11：DDL 错误独立处理

DDL 错误数据无源字段 Map（failData 为 `{BINLOG_DATA: DDLConfig JSON}`），无法使用 `SyncRow.getSourceData()`。`ErrorQueueService` 提供双入口：

- `handleFailData(...)`：DML 错误，基于 `SyncRow.getSourceData()`
- `handleDdlFailData(...)`：DDL 错误，接收 DDLConfig JSON，存储格式与重试分支（`OPERTION_ALTER`）保持不变

两入口复用公共步骤：persistError / updateCounts / notify / checkCircuitBreaker。DDL 失败同样计入 fail 并参与熔断。

**理由**：DDL 与 DML 的错误载体与重试链路本质不同，统一入口但独立数据格式。

### 决策 12：FlushStrategyImpl 只走成功路径

`FlushStrategyImpl` 改造为仅负责成功路径：成功数据异步存储（`enableStorageWriteSuccess`）+ `CounterService.incrementSuccess`；失败路径（写入、计数、通知、熔断）完全由 `ErrorQueueService` 接管，全量/增量一致。

**理由**：收敛错误处理单一职责，消除全量/增量差异。
